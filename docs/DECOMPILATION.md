# Decompilation, command reference and PSX tips

Normative extension of `../AGENTS.md`. Read this file only when that contract routes the current task here.

The shared `RotMatrix` implementation follows the packed PsyQ `rcossin_tbl` quadrant indexing and multiply/negate/shift order used by the original library routine. That table duplicates quadrant endpoints and is intentionally distinct from the scalar `rsin` quarter-wave lookup; translations must not substitute scalar `rsin`/`rcos` calls or reorder fixed-point negation and shifts without original evidence.

Perspective projection uses the PSX GTE UNR reciprocal approximation, including normalization, lookup quantization, two refinement steps and final saturation. Exact host integer division is not equivalent and can move projected coordinates even when matrices and vertices match.

## Target language and naming

Record the target language in the project's `AGENTS.md` before translation. Follow the language-specific [naming and structure rules](REFACTORING.md#naming-and-structure): C uses `lower_snake_case` functions and `UPPER_SNAKE_CASE` structure types; C++ uses `PascalCase` classes, structures, type aliases, free functions and methods, including `Effect10d::Effect10d()` and `Effect10d::ReadMasked()`. Variables, parameters and fields use `lower_snake_case` in both languages. C++ implementation files must use `.cpp`. Preserve required SDK/ABI names and linkage at mixed-language boundaries. Translate established object operations as owner methods; a `.cpp` rename alone does not fulfill object-oriented translation. These naming rules do not authorize changing the guest memory/observation contract or bypassing the refactoring entry gate.

Record the selected C++ standard in the project's `AGENTS.md` and honor it throughout decompilation. A C++98 project uses classic `virtual` declarations, unscoped enums, `0` null pointers and explicit destructor bodies; do not introduce `override`, `enum class`, `nullptr`, defaulted functions or other later-language features. Preserve required SDK/ABI types and document necessary compiler extensions instead of silently upgrading the target standard.

Use C++98 for game decompilation unless the user explicitly selects another standard. Do not silently raise the dialect for host convenience or modern formatting.

C++ function and method signatures must occupy one physical line in declarations and definitions, including the complete parameter list. Do not wrap a signature to satisfy a line-length preference. Constructor initializer lists and function bodies may use separate lines.

Default arguments are forbidden in decompiled C++ declarations and definitions. Pass every required argument explicitly at each callsite. When removing existing defaults, supply the same values explicitly and preserve overload selection and argument order. A pure virtual declaration ending in `= 0` is permitted: it is not a default argument.

Before representing an original function as an instance method, record its receiver classification from complete original caller setup, object construction and table provenance. On MIPS, an object-like pointer in `$a0` alone does not establish an implicit `this`: an ordinary function uses the same first-argument register. Validate adjusted virtual-call receiver and target pairs when present; for nonvirtual candidates, establish independent owner/receiver evidence. If the distinction remains unresolved, emit a free function in the relevant module with an explicit pointer argument. Do not claim that absence from a virtual table proves an original free or static function. Identify newly written native view/adapter helpers separately from recovered original methods.

## Reuse the existing xport SDK runtime

- This workflow produces a native game port. Existing xport PsyQ implementations are the shared, SDK-reviewed runtime; use their public APIs instead of translating SDK internals again for each game. A coverage/converge request authorizes game translation and integration, not a parallel SDK or a replacement of the shared runtime
- Use the DRAM, VRAM, scratchpad and SPU RAM already provided by xport through their existing APIs. Reusing native PsyQ wrappers does not require replacing the game's memory model. Do not create a second memory/device model or retire the provided memory domains without a separate explicit user request
- Before implementing an SDK dependency, locate its existing declaration, implementation and documented contract in xport. Match the classified original callee to the correct API and check the actual caller's arguments, result use, buffer ownership and callbacks. Do not repeat a full SDK implementation audit when the problem is caller wiring
- Keep one implementation and one owner of SDK state. Do not create duplicate `*_guest.c` modules, a second PsyQ-looking API, per-game copies of SDK algorithms/tables, or mirrors of BIOS, IRQ, SIO, DMA, GPU or SPU driver state to reproduce an original executable's memory layout
- Guest RAM equality, lockstep mismatches, original SDK scratchpad/stack writes, diagnostics and internal queues do not authorize rebuilding PS1 execution machinery or bypassing a working native API. Treat a mismatch in replaced SDK internals as a boundary-contract issue; preserve the evidence and report any comparison limitation. Never rewrite the runtime merely to make that comparison pass
- Adapt only the proven game-to-runtime boundary: argument types, bounded buffers, resource formats and callback registration. Prefer a direct existing API call. Keep unavoidable game-specific adapters and addresses in the consuming project; an adapter must delegate the SDK operation and must not reproduce its algorithm or maintain parallel SDK state
- A suspected missing feature or defect requires a concrete caller/reproducer, the existing implementation and the smallest demonstrated contract gap. Before adding a shared SDK module, replacing an existing implementation, changing SDK state ownership or expanding device emulation, present that evidence and the proposed scope for explicit user authorization. Approval for a local ABI adjustment, original-game bug fix or another subsystem does not authorize that work. Do not create a speculative replacement while awaiting authorization
- If the existing API suffices, fix the integration and retain the implementation. If a shared change is separately authorized, implement the smallest change in the existing owning subsystem, preserve unrelated consumers and validate the affected contract. Do not treat a new implementation as necessary simply because its interface resembles the original MIPS more closely
- SDK `SKIP` functions remain mapped replacements with their existing classification and evidence. Do not silently bring them back into the game translation queue, inflate game coverage with duplicated SDK bodies or claim original machine-state equivalence for native SDK calls

## Guest-memory access

Use the standard xport functions for scalar guest-memory access: `r_u8`, `r_u16`, `r_u32`, `r_s8`, `r_s16`, `r_s32`, `w_u8`, `w_u16` and `w_u32`. Preserve the original width, signedness and access order. Express a read-modify-write through an explicit standard read followed by the matching standard write; evaluate an address with side effects once in a named local.

Do not introduce project-local accessors or guest-memory lvalue macros such as `P2_U32`, even if they delegate to `psx_addr` or the standard functions. They bypass or obscure the shared memory bus and write diagnostics. Map memory with `psx_addr(address, required_bytes)` only when a native SDK/function ABI explicitly requires a host pointer; use ordinary C access for native local objects.

## Numeric literal suffixes

Do not use `u`, `l`, `ll`, their uppercase or combined forms, floating-point suffixes or other numeric literal suffixes without an explicit semantic need. Do not add them mechanically because an argument, field or result has a fixed-width type. Prefer `1`, `64` and `0x80010000` over redundant `1u`, `64u` and `0x80010000u`.

A suffix is allowed only when omitting it changes the required literal range, expression type, wrapping arithmetic, shift width, precision, overload selection or SDK/ABI contract. For example, `1u << 31` requires unsigned arithmetic to avoid a signed left-shift overflow. Establish the need from the complete expression and the original MIPS, not just the destination type; record a non-obvious reason in a brief comment or the function audit. Respect the selected language standard when choosing suffixes. Before removing an existing suffix, audit integer promotions and intermediate operations; never trade faithful arithmetic for formatting.

## Mandatory function translation audit

When complete IDA pseudocode exists, read it from its first through last line and use it as the structural baseline. A bounded excerpt, function prologue, inferred purpose, neighboring implementation or model summary is not a complete baseline. Missing, partial or unreadable pseudocode is a normal input state: set `pseudocode_complete: false` and `pseudocode_used_as_baseline: false`, then translate and audit from the complete MIPS listing. Pseudocode availability alone never accepts or rejects a function.

Audit the resulting C against the complete immutable MIPS listing before accepting WIP or DONE. Cover every basic block, branch target, delay slot, callsite, argument carrier, return value and memory side effect. Track register-carried state across calls, including nonstandard helper conventions that update argument registers, packet pointers, tags or accumulators. Audit direct local helpers in the same repair cluster when their return values or register side effects contribute to the failing function. A call alone does not require every callee listing in the owner packet: identify the specific unproved callee effect before expanding the cluster, while still auditing the owner's entire callsite and all paths.

Do not replace an original algorithm with a simpler policy, representative branch, guessed formula, fallback or placeholder. Do not defer weighted selection, pointer chaining, error paths or other reachable semantics to runtime verification. If any reachable behavior is unresolved, make no implementation claim and keep the function TODO.

For a startup translation, the attention packet must contain complete MIPS with `complete: true` and explicit pseudocode completeness metadata. The response must bind every supplied evidence hash in `decision.function_audits`, set `complete_mips_audit: true`, set `pseudocode_used_as_baseline` to the supplied `pseudocode_complete` value, and provide an empty `unresolved_semantics` list. The supervisor rejects truncated MIPS, false pseudocode completeness claims and incomplete audit receipts. It does not reject absent or partial pseudocode.

For a lockstep repair, diagnose the first divergence to identify the owning function, then audit that entire function and its state-carrying direct helpers before changing source. Follow helper calls through two levels when they carry a return pointer, mutate argument-register state, build a packet chain or otherwise determine the caller's memory effects. A patch that addresses only the observed byte, branch or call is forbidden. Make the complete audited repair as one source revision so the next fast-forward validates the whole function once.

The model receives only code-relevant evidence from the attention packet. Its prompt includes complete original MIPS, available pseudocode with an explicit completeness flag, the currently mapped C function, machine-check IDs, the bounded difference and writer observations, plus local C helper bodies reached from the mapped implementation within two calls. Build and record identities remain with the supervisor. If a helper body is needed but absent or changed, the prompt fails before invoking the model; do not ask it to infer the missing C implementation.

Attention packets bind the owning function and the two-level same-image helper cluster by exact function and MIPS hashes, plus a pseudocode hash when pseudocode exists. The model returns one proposal containing C/H substitutions and complete audit entries for every required function. The supervisor alone applies owned source changes and writes the sibling `attention-NNNN.audit.json` receipt with contract `xport-lockstep-function-audit-v1`, resulting source identity and exact changed-file set. Each entry must report pseudocode completeness and baseline use consistently, confirm a complete MIPS audit and contain an empty unresolved-semantics list. Direct source edits outside the supervisor are rejected before another replay.

New attention packets also contain `machine_audit` for each required function. It is derived from raw instruction bytes, including multiword IDA pseudo-instructions, and lists calls, control transfers, delay slots, guest loads and stores. A bounded scan also flags argument registers read after a call before local redefinition, since a helper may carry nonstandard state through them. Each function audit receipt must copy `machine_audit_sha256` from its required binding and provide `machine_coverage` groups. Each group contains either `check_ids` (one to eight IDs) or `check_range: [first, last]` (zero-based inclusive positions for one to eight adjacent sorted machine checks), `source_file` (a project-owned source or header file in the current source snapshot), and a nonblank one-based `source_line`. Every check ID must appear exactly once across that function's groups. This is a structural coverage check; it cannot certify that the mapped C expression has correct MIPS semantics. Historical packets without a machine checklist retain their prior receipt format.
For a mapped translated C function, each coverage group also names `source_symbol`. The validator reparses current C source and requires the mapped line to lie inside that function or a helper reachable through an unambiguous direct C call. A marker line, unrelated function, or stale source location cannot stand in for an instruction mapping. Update `source_symbol` from the prefilled translated function to the actual reachable helper when a MIPS operation is implemented there. This remains a structural check, so full semantic review and replay are still mandatory.

When the proven final writer is a reviewed PsyQ library function with its effects inlined in game C, its complete original MIPS becomes a second required function audit; available pseudocode remains supplementary evidence with explicit completeness metadata. The receipt must map every library machine check to a concrete line in the owning translated C function or a reachable helper. The owner binding remains required; an unrelated function cannot satisfy either mapping. A saved packet with no model invocation may be upgraded to this audit contract without emulator replay.

The supervisor generates the source-bound audit receipt from the model's complete `function_audits` after applying code. The receipt template starts with false audit booleans and unresolved semantics; validation accepts it only when every required row and machine check has been completed and mapped to a current C line. On audit or LockstepDebug compile failure, the supervisor restores the preceding source bytes and receipt before any replay. A successful compile is part of acceptance, while full-record lockstep remains the behavior proof.

For manual converge repair, the auditing agent reads the full game and shared source context, then submits exact code substitutions and complete audit rows as `repair-proposal.json` by atomically renaming a complete temporary file in the converge run directory. The supervisor validates unique source anchors, owned paths, unchanged baseline and all audit rows before accepting it. `repair-proposal.result.json` reports application or rejection. The auditing agent must not directly edit game or shared source while the supervisor is waiting.

`code_refresh`, compilation and source-index success are structural checks. They are never semantic evidence. Runtime convergence validates an already complete static translation; it must not be used to discover omitted blocks one at a time.

For a bounded owner audit, `tools/mips_function_fixture.py` can execute original raw words with MIPS-I branch/load delays and explicitly supplied external-call fixtures. It rejects unsupported instructions, control transfers in delay slots, data outside aligned cached 2 MiB RAM and instruction-limit exhaustion. The explicit `allow_ram_aliases=True` fixture option additionally accepts the physical and KSEG1 aliases of that same RAM while retaining original addresses in the access trace; scratchpad, MMIO and ROM remain rejected. MULT/MULTU, DIV/DIVU and MFHI/MFLO model result words, including divide-by-zero and signed overflow; HI/LO timing remains outside fixture scope. BREAK terminates the fixture with its encoded code before subsequent instructions; it does not emulate the exception handler. It is a limited audit fixture, not a complete PS1 CPU. A project comparison must bind the original function bytes and actual C/header/fixture hashes, compare all owner boundary carriers and ordered guest data accesses, and declare every external fixture limitation. Fixture MATCH corroborates the static owner audit; it cannot certify unimplemented callees or full-game runtime equivalence.

Signed `ADD`, `ADDI` and `SUB` reject signed 32-bit overflow before writing their destination, including register zero. `ADDI` sign-extends its 16-bit immediate; `ADDIU` remains wrapping arithmetic. Overflow stops the fixture with `ValueError`; it does not emulate CP0 exception state or a guest exception handler. Run `python -B -m unittest tools.tests.test_mips_function_fixture` from the toolset root after changing instruction semantics.

## Full-pass translation and batch modules

This is the canonical source-allocation and execution policy for ordinary decompilation and `coverage NAME`. More specific user scope and platform restrictions take precedence. Do not apply this full-pass schedule to a requested isolated repair or an explicitly requested strict proof/converge task.

### Scope, order and saved source

- Fix the selected image-qualified game-function set before the pass. Use the function recording's immutable first-call order first, then a deterministic address order for remaining functions in the declared scope. Do not silently expand into deferred images or omit unrecorded functions from an explicitly full-image task
- Inventory existing complete bodies and reviewed shared SDK replacements once. Resume them in their current modules; do not retranslate or relocate unchanged functions to adopt a new naming scheme. Keep one signature registry and update it when original caller/callee evidence changes
- Translate the entire selected set before integration. Save each complete original function immediately, with its image-qualified `FUNCTION_MARKER` and source/provenance binding. Preserve original arithmetic, widths, aliases, branch/call order and error returns; use complete pseudocode where available and original MIPS as semantic authority
- Keep calls to pending game functions as ordinary declared calls. Missing implementations and unresolved symbols are expected during the pass; do not compile early, insert successful stubs, guess implementations or stop the pass at the first unimplemented callee
- Record genuine semantic gaps explicitly and continue with independent functions. A prototype, partial body, TODO or abort stub is not a complete translated function and cannot close the pass

### Sequential module allocation

- For new C translations use `src/batch_1.c`, `src/batch_2.c`, and so on, with consecutive numeric suffixes. Keep an existing entry/bootstrap module in place. A user-authorized C++ translation uses the same sequence with `.cpp`; honor the recorded language
- Resume the last active sequential module. Before appending the next complete function, count its existing physical lines, including includes, comments and blank lines. If it already has more than 2000 lines, create the next module and append there; otherwise append to the current module
- The threshold is soft. Do not predict whether the next function will exceed 2000 lines. A module at exactly 2000 lines still receives the next complete function; a module at 2001 lines starts the next module before the next function
- Keep each original function whole. A function that takes its module past the threshold, including a function longer than 2000 lines by itself, stays entirely in that module. Start the following function in the next module; do not split bodies or rebalance previous modules
- Module size is independent of a tooling packet's function count. There is no fixed number of functions per source module and no 16-function translation or build checkpoint
- Save needed declarations/includes and record new modules as integration inputs during translation. Defer complete build-project registration, caller/SDK wiring and link repair to final integration; recording inputs does not require a build

### Deferred integration and verification

- During the full translation pass do not compile, build, run the game, run runtime tests or invoke build/check/index pipelines after functions or modules. Do not use `code_refresh`, even with skip flags, as a per-module checkpoint. Original-source reading, MIPS/ABI/alias analysis, signature edits, physical-line counting and manual provenance maintenance remain implementation work
- Do not stop to integrate a completed module or dependency cluster. Continue until every selected function has a saved full body or an explicitly reviewed existing implementation/replacement. Unresolved semantic bodies remain an incomplete pass, not a reason to claim completion
- Begin integration after the whole pass: register all new modules, reconcile declarations/callers/callbacks and SDK boundaries, remove duplicate implementations and classify dependencies outside the selected scope. Preserve the scope denominator and historical evidence
- Then run the complete applicable indexing/marker checks, Debug build and agreed native scenarios. Repair real compile/link/runtime failures from original evidence; repeat affected checks after fixes. Final integration and repair may require several builds, but none are per-translation-batch gates
- Run final Release or other platform builds only as required by the agreed task scope; a narrower user restriction prevails. Builds and observed scenarios prove only their actual scope, never automatic original equivalence
- Mark draft bodies unverified until the relevant final checks succeed. Preserve historical receipts and invalidate changed-source proof reuse. A full translation pass alone does not complete an integration/runtime deliverable

## 8. WIP → DONE and regression gates

DONE requires image-verified static MIPS audit plus compatible dynamic evidence in a declared context/range. Record coverage gaps explicitly; one context is not proof of every character/level/branch. SKIP requires justified replacement scope and its validation, not a missed call. TODO is no accepted implementation; WIP includes incomplete or insufficiently proven implementations.

For ordinary translation, follow [Full-pass translation and batch modules](#full-pass-translation-and-batch-modules). Its soft source-module threshold and deferred integration replace the former hard 2000-line admission limit and indivisible 16-function source batches. Explicit strict-supervisor transactions retain their separate implemented contract in [COVERAGE_STRICT.md](COVERAGE_STRICT.md); they do not define the default translation workflow.

For PsyQ, never assign SKIP by recognizing a familiar `.lst` body, IDA name or call pattern. The immutable listing supplies the exact image/address and original instructions; the reviewed Ghidra masked-signature classification supplies SDK identity. Confirm both layers with `X query 0xADDRESS --image IMAGE`: `function.status` must be `SKIP` and `library_classification` must name the alias, reason and evidence. Pending/ambiguous signatures remain TODO. The complete initial classification and listing-to-SKIP procedure is in `STARTUP.md`.

Compare the entire declared range, expected counts, selected structures, ordered calls and arguments. Inspect `passed`, `partial`, channel scope and first difference; exit zero alone may not mean PASS. State/GPU-command/sound-call matches do not prove pixels/PCM, unhooked intervals or all inputs. No silent masks, input suppression or fake success. Preserve raw GPU differences; exclude only audited unused fields.

On accepted change update implementation/evidence links, coverage and hashes; invalidate stale dependencies without deleting history; rebuild derived SQL/progress. Use once-only markers to prioritize level coverage, never as correctness gates. WIP summary frequencies include every call; expand targets through dependencies, then strict replay to distinguish primary failures from consequences of prior skips.

- Project lifecycle: `doctor`, `convert_music`, `startup.py`, `prepare.bat`
- Build and evidence: `coverage NAME`, `build_native`, `build_database`, `render_progress`, `code_refresh`, `source_index --rebuild`, `source_context`, `query --audit-context`
- Record + converge: `record SLOT NAME`, `stop`, `record.ps1 -Action start/stop/status`, bounded `trace_workflow record STATE_PATH NAME --frames N`, and `trace_workflow converge NAME`
- Lockstep diagnostics are generated by `lockstep_supervisor` and `lockstep_project_runtime`; do not launch separate temporary capture workflows
- Use static MIPS and causal audit helpers whenever required to complete translation, migration, coverage or converge. A missing lockstep attention packet does not require a separate audit request. Bind each audit to complete original evidence and keep static findings separate from dynamic MATCH evidence

The public recorder accepts an exact save state and stores only its immutable copy plus effective controller state at each FrameDone. Converge restores that state, replays the input sequence and compares semantic events followed by DRAM and scratchpad. A mismatch packet supplies the exact callsite address and instruction, delay slot, listing, pseudocode, current C, invocation path and bounded writer evidence.
## Reviewed indirect call edges

Projects may bind `analysis.resolved_indirect_calls` to a project-local JSON manifest with schema `xport-reviewed-indirect-calls-v1` and an `edges` array. Each edge contains `image`, integer `source`, `site`, `target`, `image_sha256`, `source_sha256` and `proof`. A `reviewed_vtable_slot` proof contains a project-local review `path` and `sha256`, integer `constructor`, `constructor_sha256`, integer `table`, `slot_offset`, signed `receiver_adjustment`, exact eight-byte little-endian `slot_bytes`, and `complete_target_set: false`. The review must establish the constructor's table assignment and the complete caller's receiver/slot/target loads from original MIPS, using full available pseudocode as its structural baseline. A pointer word alone is not a dispatch proof.

A `reviewed_callback_argument` proof uses the same review path/hash and `complete_target_set: false`, plus `caller`, `caller_sha256`, `call_site`, `argument_register`, two `argument_setup` entries with integer `site` and hexadecimal `word`, and `callback_binding` with `site` and `word`. The supported setup is LUI followed by ADDIU in the direct call delay slot; the caller must call the reviewed source. The callee binding must copy that argument into the JALR target register. Review the complete original bodies to establish control flow, absence of intervening clobbers and callback argument semantics. Validation checks these local encodings and identities; it does not prove reachability, accept ambiguous caller boundaries or close unknown targets.

`build_database` rejects changed image/function/review hashes, non-JALR sites, missing original functions and mismatched table slots. Accepted alternatives become `indirect_reviewed` edges with SQL `edge_provenance`; their sites remain `partially_resolved_static`. They are possible static dispatch edges, not observed calls or exhaustive target sets. Missing manifests preserve the direct graph. Keep unreviewed indirect alternatives unresolved; do not infer dead code from a missing graph path. Rebuild SQL and progress after the connected implementation pass to display the reviewed edges.

Projects may bind `analysis.function_scope` to a project-local `xport-function-scope-v1` JSON document with `image` and `rows`. Each row contains the eight-digit hexadecimal `address`, `original_sha256`, `category` and `reason`. Categories are `needed`, `possibly_needed`, `replaced` and `dead_code_candidate`. Keep evidence and uncertainty in additional row fields. `render_progress` rejects duplicate/stale identities, displays queue scope separately from TODO/WIP/DONE/SKIP, and displays available native source mappings. Candidate exclusion affects the current translation queue only; a missed observation never proves unreachability, and a scope label never grants SKIP, DONE or semantic equivalence.

## Minimal CTree sidecars

`ida/ida_analyze_export.py` accepts an optional bounded `ctree_addresses` list. For each successfully decompiled address it writes `ctree/ADDRESS.json` with contract `xport-ida-ctree-v1`: statement/expression kind, numeric and named operation, type text/width/signedness, parent and child identities, local-variable identity/location, node EA when available, prototype, reviewed GP, function hash and original image identity. A missing node EA is stored as `null` with `unsupported_source_map_gap`; it is never replaced by a guessed instruction.

Projects bind derived sidecars through `analysis.ctree_exports`. `build_database` validates the schema, original image bytes and current image-qualified function hash before populating `ctree_functions`, `ctree_lvars` and `ctree_nodes`. The CTree database is structural evidence for dereference/index recovery and source mapping. It is not generated C, a complete mapping, or proof that Hex-Rays types and control flow are correct.

Run a real installed IDA/Hex-Rays export before claiming support. Python schema tests cover only the import contract. Keep the new IDB/export under status as derived evidence; do not overwrite the original canonical exports.

## Reviewed CTree-to-C candidates

`ctree_to_c.py` translates only `xport-ida-ctree-v1` sidecars covered by an exact `xport-ctree-transform-v1` manifest. Version 1 supports fixed-width integer expressions, wrapping arithmetic, assignments, 8/16/32-bit guest loads and stores, if/else, loops, and direct calls with a node-specific reviewed prototype. Guest addresses remain `uint32_t`; host pointer arguments require the distinct `host_pointer` manifest kind. Unsupported widths, address forms, intrinsics, indirect calls, or ABI assumptions produce a node-specific gap in `report.json`.

The output directory must be outside every `src` path. A manifest may bind a proposed application only by exact existing-source SHA-256 and `reviewed: true`; generation itself never changes hand-edited source. Review rejects register arrays, instruction-shaped macros, and switch dispatchers. Names and layouts may be refined after the generated baseline passes behavior tests.

Use `ctree_z3_verify.py` only for a short expression with an independently written MIPS semantic AST and explicit preconditions. Missing `z3-solver`, timeout, unknown, or a counterexample is not a pass. Keep development and holdout fixtures under `tools/tests/fixtures/ctree_to_c`; both sets must compile with MSVC warnings as errors. An unsupported CTree sample must produce an explicit gap and must never be rewritten or promoted to project source.

## 10. Tips: PSX/MIPS/IDA

These are platform facts and audit checks, not game addresses or blanket normalization permissions.

- When a PsyQ symbol collides with a host API or macro, give the canonical shared wrapper a `PSX` suffix and use that name in translated game code. Preserve the original PsyQ identity in classification and audit evidence; do not solve the collision with include order or `#undef` of the host API. Canonical example: PsyQ `LoadImage` becomes `LoadImagePSX`, while Win32 keeps `LoadImageA`/`LoadImageW` and its `LoadImage` macro.
- Keep original PsyQ names on the public compatibility surface when the implementation preserves that API's contract. Implement that entry directly in the owning shared subsystem; do not insert one-line `psx_*` or `xport_*` forwarding trampolines between game code and the implementation. Use `gpu_*`, `spu_*` and `gte_*` consistently for internal subsystem functions, types and constants, and reserve `xport_*` for genuine host services and required game bindings beneath that surface. Do not retain a parallel `PsyQ*` or `psx_gpu_*`/`psx_spu_*` compatibility layer with duplicate state, give an internal binding a second PsyQ-looking name or treat a host adapter as proof of original PsyQ behavior.
- A converge repair may change a game C/H file and an existing shared `xport/src` C/H file in one supervisor transaction. Name shared paths with `@xport/src/` in the proposal and map each original MIPS effect to a real line in the owning translated function or a reachable shared helper. The original listing remains the authority for both trees; a historical SDK body alone cannot justify a shared wrapper change.
- Do not merge PsyQ routines merely because their names or resulting command words are similar. Bind the exact classified callee address and audit observable packet layout. In particular, keep one-word draw-mode construction distinct from the two-word draw-mode-plus-texture-window macro; a null texture-window argument does not prove that the original call used the one-word routine.
- Preserve exact integer lookup data for classified PsyQ numeric routines. Extract or verify the SDK table against the immutable game image; a floating-point-generated approximation is not equivalent even when it differs by only one fixed-point unit.
- Do not publish an unused PsyQ entry as a body of `(void)parameter` suppressions. Implement the modeled contract, register a deliberate WIP through the project policy when the game reaches it, or omit the unneeded entry until a real consumer and implementation exist.
- Preserve the original PsyQ `LIBETC.H` controller names and aliases, including `PADi` through `PADo`, `PADh`, `PADL1`, `PADL2`, `PADR1`, `PADR2`, `PADstart`, `PADselect` and `_PAD(controller, button)`. Do not replace SDK names with a modernized naming scheme.
- Little-endian MIPS I: audit branch delay instructions on both paths, including JAL/JALR/JR; link address and nonstandard link register matter. A pending load can leave the next instruction using the old register. Respect HI/LO, sign-vs-zero extension, SRA/SRL and signed/unsigned comparisons. Translate wrapping arithmetic without C signed-overflow UB; implement unaligned LWL/LWR/SWL/SWR merges explicitly. Do not replace division/multiply corner behavior with unchecked host operations. [CPU reference](https://psx-spx.consoledev.net/cpuspecifications/)
- Treat the PS-X EXE header GP as a hint, not authority. The accepted IDA profile must contain a nonzero runtime GP plus reviewed evidence that agrees with the loaded image. Accept the unique adjacent `lui $gp`/`addiu $gp,$gp` initializer or another explicitly named derivation with equivalent byte evidence. Zero, ambiguous, inherited without reviewed evidence or mismatched GP fails before IDA export; never generate pseudocode first and repair its base later
- For every `$gp` memory operand, compute the effective address as `runtime_gp + sign_extend(imm16)` from the immutable listing. Run `X gp_audit --report status/audits/gp-address-audit.json` after translating a frontier that contains GP-relative accesses. Any wrong or inferred base must be corrected before acceptance. A missing literal may be valid only when the C body demonstrably represents the same access through an indexed contiguous range, a copied aggregate, an unreachable original instruction or an explicit WIP gap; record that classification and do not promote an unresolved WIP function to DONE
- Main RAM is 2 MiB with cached/uncached aliases. Scratchpad is separate 1 KiB at `0x1F800000..0x1F8003FF` (cached mirror `0x9F800000`); do not treat the KSEG1 scratchpad range as ordinary RAM. Do not apply `addr & 0x1FFFFF` to arbitrary addresses: it aliases scratchpad, MMIO and BIOS incorrectly. VRAM and sound RAM are separate device memories. Overlay/self-modifying code requires cache/context awareness; stored RAM bytes need not equal cached instructions currently executing. [Memory map](https://psx-spx.consoledev.net/memorymap/)
- Decode fixed hardware addresses through a typed bus, not guessed host pointers: GPU GP0/GP1 `0x1F801810/814`, pad/memory-card serial `0x1F801040`, interrupt and DMA/timer regions per I/O map. Hardware access width/order can matter; do not model all registers as normal memory. [I/O map](https://psx-spx.consoledev.net/iomap/)
- VRAM is 1024×512 16-bit storage; coordinate/address units depend on pixel/texture format. Preserve CLUT/tpage/texture-window, draw offset/area, mask/semitransparency/dithering and packet order. Check DMA/OT pointers and terminators before dereferencing; packet header length differs from payload length. VRAM transfers must work even with raster disabled. Raw textured packet RGB and padding require opcode/layout-specific proof before comparison exclusions. [GPU reference](https://psx-spx.consoledev.net/graphicsprocessingunitgpu/)
- GTE is stateful: preserve control/data registers, MAC/IR arithmetic, FIFO effects, saturation/FLAG and fixed-point conventions. Replacing transformations with floating point can change branches as well as pixels. Include GTE state in checkpoints. [GTE reference](https://psx-spx.consoledev.net/geometrytransformationenginegte/)
- Audit GP initialization per executable/overlay before trusting global accesses. Caller conventions, stack arguments, preserved registers and real structure stride beat inferred prototypes. A pointer in a0 is not evidence of C++ `this`; a table of pointers is not automatically a vtable.
- IDA can infer wrong function boundaries/chunks, stack deltas, prototypes, signedness, structure sizes, array stride, tail calls and jump-table targets. Inline assembly, reused registers and overlapping data/code can invalidate pseudocode. Never implement guessed `undefined` types literally. Fix metadata only with byte/caller evidence; preserve the initial export and failures. Validate pseudocode-reordered delay-slot side effects against raw instruction order. These are audit risks, not a claim that every MIPS decompilation is wrong. [Hex-Rays MIPS examples](https://docs.hex-rays.com/user-guide/decompiler/introduction-to-decompilation-vs-disassembly/comparisons-of-mips-disassembly-and-decompilation), [failure handling](https://docs.hex-rays.com/user-guide/decompiler/failures)
- Native pointers/host endian/alignment differ from guest addresses. Use explicit load/store helpers and documented guest struct offsets; never serialize raw host pointers/padding into portable checkpoints. Clear/reuse scratchpad only as original code does, not at every function/frame.
- VBlank, GPU submission, game logic tick and menu/sequence phase may differ. Preserve callback ordering/RNG/time during accelerated runs; PAL/NTSC rates and phase resets are project facts. Do not align solely by wall time or equal frame numbers.

- Immediate reconstruction: `LUI imm16` produces `imm16 << 16`; audit hex digit positions before transcribing constants. For `SRA`, cast the complete wrapped 32-bit expression to a signed type before the shift, not after an unsigned shift.
When translating inline GTE projection followed by `AVSZ3` or `AVSZ4`, use `gte_project_full_depth` for each projected vertex before `AverageZ3` or `AverageZ4`. `gte_project` and `RotTransPers` return the PsyQ `SZ3 / 4` result and must not be substituted for the full GTE `SZ` FIFO values consumed by the averaging opcodes.
