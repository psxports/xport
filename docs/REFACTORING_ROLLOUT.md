# Refactoring v2 redesign and adoption plan

Scope: the workflow agreed with the completed Apocalypse project. Preserve every authorized delivery requirement, original evidence and active goal; reduce repeated analysis, edits and reporting. No game migration, game builds or user sessions are owned by this rollout.

## Implementation sequence

1. Publish change classes and evidence reuse in `REFACTORING.md`: relocation, representation/ABI, behavior; distinguish source consistency from semantic/runtime acceptance
2. Preserve entry/terminal gates, native ownership, numeric/device contracts and agreed architectures. Put technical details in `REFACTORING_CONTRACTS.md`; read only affected sections and preserve old anchor routes
3. Define one family contract and one current project plan; meaningful names/types/owners immediately, one planned exhaustive editorial pass, one planned fixture adaptation after stable interfaces
4. Separate allowed static tools from compilation/execution. Preserve existing final-only compilation restrictions; optional compile-only policy requires compatible project/user authorization. Full code_refresh and runtime acceptance remain final
5. Publish `refactor_source.py`, reusing the shared source parser and Apocalypse's explicit-map body-preservation approach. Compare a bounded family to its existing ZIP; do not transform game sources, update SQL, introduce fixture adapters or infer equivalence
6. Verify maximal tokens, strings, image-qualified markers, missing/duplicate identities, map scope, report paths and read-only inputs. Exercise a real Apocalypse baseline/current sample without changing that project. Validate local documentation links and policy consistency
7. Notify current refactoring chats, help each map its current phase/restrictions to v2, resolve adoption questions and confirm an in-place transition. Do not restart completed projects or treat refactor percentage as structural completion

## Existing-agent transition

Recipients are determined from current thread context, not all projects in a sidebar section. Known running refactor chats at rollout: FightingForce, TestDrive5, AgentArmstrong. Recheck live tasks before closing the rollout; inspect ambiguous titles only enough to identify an active refactor goal. A sleeping coverage/enhance chat is not a refactor recipient solely because of historical work.

At the next coherent save boundary each recipient:

1. Read workflow v2 and only applicable technical contracts; preserve current goal, user authorization, source baseline, accepted results, original markers/ledger and explicit final scope
2. Update the existing plan/current context with `workflow_version: 2`, current phase/family, `compile_policy`, pending families/editorial work, agreed targets, qualifications and final gates. No duplicate reporting hierarchy or retrospective full audit
3. Keep explicit final-only compilation policies. Finish the current connected family; classify further edits and reuse already covered analysis. Do not schedule compilation, new runtime trials or fixture maintenance merely to adopt the document
4. If a body-preservation comparison would save rereading, use the existing ZIP, explicit baseline/destination files and reviewed map. A mismatch requests scoped review; it is not an instruction to undo native work. Rename maps never authorize semantic changes
5. Resume the correct existing phase. Do not return already-native/final-verification work to the start, adopt a new architecture silently, or repeat unchanged passing checks. Carry required targets and known limitations unchanged
6. Confirm adoption with a short chat update or current-context record naming phase, compile restriction and the immediate next family/action. Raise concrete blockers; continue independent work

## Assistance and acceptance

- Provide exact tool/contract commands for each agent's actual source/baseline layout when requested; support existing C and C++ plans without forcing a new file organization
- Diagnose tooling/document inconsistencies centrally. Agents retain game semantics and project edits; do not take over their decompilation or create substitute project audits
- Completed Apocalypse remains a reference and is not reopened. Its historical x86 acceptance does not prove x64
- Completion: documentation and static tool tests pass; real-source limitations are recorded; current refactor recipients receive final instructions and acknowledge or demonstrate v2 adoption; concrete adoption blockers receive a resolution or an explicit pending human/external requirement. Active gameplay refactor goals themselves need not finish for this tooling rollout to complete
